# PERF-008.2 — Инкрементальное autosave и публикация по ревизии

Дата: 08.09.2026. Реализация подключена для company/system builder за серверным
`BUILDER_SAVE_V2`, default false. Локальные проверки пройдены. Внешняя БД и реальные env
не изменялись. **Production rollout и общая performance-приёмка ещё не выполнены.**

## Реализация

- Начальная версия, содержимое и строковая bigint revision берутся из одного защищённого
  snapshot RPC. Предварительный loader страницы читает только метаданные, не дублирует
  загрузку вопросов. Preview и V1 сохраняют прежнее чтение.
- Клиент сравнивает документ с последним ACK и держит pending batch изменённых/удалённых
  ID. Секции не включают questions, вопросы не включают options. Один option edit
  отправляет только этот option; локальная сериализация/diff выполняется при flush,
  не при каждом нажатии клавиши.
- Debounce — 2 секунды **после последнего изменения**; один in-flight request. Изменения
  во время запроса не теряются и отправляются следующим пакетом после его подтверждения.
- При временной ошибке — максимум 3 попытки с паузами 500/1000 мс. Если результат неизвестен,
  ручной повтор использует тот же request ID, expected revision и неизменный payload.
  Последующие правки ждут ACK старого пакета. Validation error разрешает исправление;
  revision conflict блокирует запись, без автоматического rebase или V1 fallback.
- Внутри server service после auth — один snapshot RPC и один commit RPC. Сервер собирает
  итоговый документ, выполняет прежнюю Zod/domain/remediation-валидацию, очищает rich text,
  вычисляет storage delta и записывает его одной транзакцией. Содержимое для валидации
  пока читается целиком **на сервере**; это не обещание O(1) server CPU/read bytes.
- Перед preview/publish выполняется flush. Во время публикации редактор заблокирован,
  в том числе contenteditable. Существующая проверка correctness, structured questions и
  scoring V2 выполняется по snapshot; RPC публикует только совпавшую expected revision.
  Изменение после проверки приводит к конфликту, а не к публикации непроверенного состояния.
- Потерянное подтверждение публикации допускает повтор с тем же ID. До выяснения результата
  редактирование заморожено. Публикация системного теста и audit event атомарны.
- Публикация из карточки теста также использует V2 validation/CAS. Параметры draft при
  включённом V2 редактируются через конструктор: карточка даёт ссылку вместо старой формы.
  Уже открытые V1-формы получают пояснение, а не пытаются обходить revision protocol.
- Чистая terminal-архивация и удаление draft сохраняют прежние проверки ownership/RLS
  и immutable/used-content. Архивацией нельзя одновременно изменить metadata. После
  архивации/удаления запоздавший save не может вернуть версию в draft.
- `builder.save` / `builder.autosave` telemetry сохранена; никакого текста вопросов в ней нет.

## Что исправлено при перепроверке

1. Старые черновики могут иметь нулевые, разреженные и совпадающие order_index. Простое
   изменение текста больше не заменяет такой индекс порядковым номером и не переставляет
   вариант случайно. Новые индексы назначаются только при изменении порядка/состава siblings.
2. Неправильная строка revision, включая дробь/текст/переполнение bigint, даёт validation
   error, а не исключение BigInt внутри safeParse.
3. Пакет больше 900 000 UTF-8 bytes отклоняется до отправки: запас под служебную оболочку
   текущего Server Action limit 1 MiB. Dirty-документ остаётся доступным; можно скачать копию
   и уменьшить пакет. Нет бессмысленных сетевых retries слишком большого запроса.
4. HTML-тест исправлен на реальный rich-text формат `<!--talora-rich-text-v1-->`.
   Строки без маркера по прежнему контракту являются plain text и экранируются при выводе;
   их не следует ошибочно считать HTML. Форматированный HTML очищается реальным sanitizer.
5. Проверена совместимость регистрации V2 с существующими archive/delete и карточками версий.

## Локальная копия и ошибки

Кнопка «Скачать локальные изменения» выгружает актуальный документ и базовую ревизию
в `talvia.builder.recovery.v1` JSON. Это **резервная копия для ручного восстановления**, не
файл `talvia.test.v1` для мастера импорта; автоматический merge/import recovery не реализован.
При конфликте сначала скачать копию, затем обновить страницу и перенести нужные правки.

При несохранённых изменениях добавлен beforeunload для закрытия/обновления вкладки.
Документ не пишется автоматически в localStorage и не переживает закрытие вкладки.
Перед внутренней навигацией/кнопкой «Назад» дождаться ACK или скачать копию: beforeunload
не гарантирует защиту от SPA-переходов. Dirty/error нельзя трактовать как успешное сохранение.

## Проверки

- Полный Node suite: **462 tests passed**, включая 36 тестов текущего V2 storage,
  service/controller/contract и авторизации (с родительскими тестами).
- PGlite исполняет обе реальные миграции: rollback, conflicts, ACK, permissions, ownership,
  metadata/order, consistency snapshot, publish race, audit rollback, terminal archive/delete.
- Browser component suite: **8 сценариев редактора** (профилирование + 3 прежних + 4 V2),
  **8 прежних сценариев импорта**. V2: 100 вопросов/one-option payload/trailing debounce,
  flush перед publish, conflict/export/beforeunload, потерянный publish ACK.
- Lint, typecheck и production build пройдены.

Это локальный PGlite и настоящий React в изолированном Chrome с синтетическими server
actions, **не** end-to-end Supabase/Next и не два конкурентных PostgreSQL подключения.
Проверки ролей в БД и wrappers не заменяют full RLS staging-матрицу. Browser timing не INP
и не production p95. Реальные network bytes/latency, concurrency/deadlocks и auth/session
expiry необходимо проверить перед rollout. Без этого PERF-008 performance acceptance открыт.

## Staging — порядок включения

1. Сначала deploy совместимого кода с `BUILDER_SAVE_V2=false`; закрыть старые редакторы.
2. На полностью мигрированном staging применить по порядку:
   - `supabase/migrations/20260908120000_builder_save_v2.sql` (если ещё не применена);
   - `supabase/migrations/20260908140000_builder_save_v2_integration.sql`.
3. Выполнить read-only проверки:
   - `supabase/verification/builder_save_v2.sql`;
   - `supabase/verification/builder_save_v2_integration.sql`.
   Все `passed` должны быть true; `unfinished_writes` — 0. До тестовых V2-записей
   `enrolled_versions` также должен быть 0.
4. В **staging**, не production, установить `BUILDER_SAVE_V2=true` и перезапустить/deploy app.
5. Для компании и системного теста проверить: обычное сохранение, все типы вопросов,
   copy/import/delete/move, настройки версии, preview, publish из редактора и карточки,
   archive draft, удаление неиспользованного теста, отмену неиспользованной system-публикации.
6. Проверить два редактора с одной исходной revision; save во время publish; разрыв сети
   после commit; повтор публикации; viewer/disabled/revoked member; чужие UUID/parent IDs.
7. На 100-question draft снять payload и latency: один option edit не содержит остальных
   вопросов. Сравнить server/client telemetry с baseline, не считать локальный тест p95.

`tests/fixtures/*.sql` **не запускать в Supabase SQL Editor**: это локальные заглушки,
не миграции. Флаг по умолчанию выключен; эта работа не применяла миграции удалённо.

## Откат и ограничения

Первая успешная V2 запись/публикация регистрирует версию в `builder_save_state`. Старый
writer больше не может менять её содержимое/публиковать без revision. Выключение flag —
**аварийная пауза для зарегистрированных draft, не возврат к V1**. Старые draft без
регистрации сохраняют V1-поведение. Нельзя удалять строки регистрации ради обхода защиты.

При проблеме остановить редактирование, сохранить локальные копии, отключить flag и
разобрать причину на staging. Для восстановления работы зарегистрированных draft нужен
исправленный совместимый V2 код. Полный downgrade требует отдельной согласованной процедуры
при закрытых редакторах, а не автоматического fallback в обработчике ошибки.

Большие добавления/импорты могут потребовать сохранения небольшими порциями из-за HTTP
лимита. Ни bodySizeLimit всех Server Actions, ни зависимости проекта не расширялись.

Следующий обязательный шаг для выпуска — staging-приёмка выше. Следующая кодовая задача
плана — PERF-009 (атомарное клонирование версии); она здесь не реализовывалась.
