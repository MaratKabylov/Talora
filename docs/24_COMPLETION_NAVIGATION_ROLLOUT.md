# PERF-005d: завершение и переход между тестами

## Изменения — 08.09.2026

Серверный флаг `ASSESSMENT_COMPLETION_V2` включает новый путь ручного завершения для
candidate/employee: режим одного вопроса, целой секции и пустой тест. По умолчанию выключен.
Предзагрузка из шага 23 независима: ее миграция и флаг для завершения не требуются.

После подтвержденного finalize/batch клиент отправляет `POST /api/assessment/complete`
с token/session/client/device, **без ответов**. Один `complete_assessment_session_v2` RPC:

- Проверяет company/owner/person/context/session, приглашение, согласие, статус и lease.
- Под блокировкой сессии проверяет сохраненные видимые ответы через нормализатор V2.
  В one-question обязательны строки всех видимых вопросов, включая явный optional skip.
  В section отсутствующие необязательные ответы допустимы, обязательные и активная
  remediation должны быть заполнены. Неполные structured drafts не считаются завершенными.
- Завершает текущую сессию, фиксирует время/reason и очищает ее lease. Ответы не переписывает.
- Выбирает уже запущенный тест либо первый незапущенный в прежнем порядке пакета/назначений,
  запускает его и возвращает ID. Повторный запрос не сбрасывает started_at/deadline.
- Если все назначенные сессии completed, возвращает server-only идентификаторы для скоринга.

Блокировки берутся в порядке owner → invitation → session. Owner `FOR UPDATE` сериализует
V2-завершения одного участника; блокировка берется сразу, без повышения shared-lock после
захвата session. Ошибка записи или истечение token/deadline внутри медленного trigger
откатывает завершение, старт следующей сессии и обновление lease. Проверка lease использует
существующий RPC V2. Сам новый RPC не считает баллы, не возвращает вопросы/ответы/scoring keys.
Права: `SECURITY DEFINER`, пустой `search_path`, execute только `service_role`.

Правила допуска/порядка соответствуют overview V2: candidate — опубликованные версии
текущего пакета; employee — закрепленные назначения с прежним fallback порядка, включая
архивированные версии. Готовность скоринга проверяет **все** назначенные сессии, как старый
finalizer, а не только видимые в текущем пакете. Cancelled/expired назначения не превращаются
в completed: если нет следующего допустимого теста, возвращается стартовая страница.

## Скоринг, повторы и навигация

На последнем тесте сервер вызывает прежний `finalizeCompletedCandidateAssessment` или
`finalizeCompletedEmployeeAssessment`. Движок, формулы, report persistence, scoring claim
и его TTL не изменены. Финализация остается синхронной; фоновых очередей этот шаг не добавляет.

Завершение сессии/старт следующей атомарны, но финализация результатов выполняется **после**
этой транзакции. Если RPC успел зафиксировать completed, а сеть/скоринг дали ошибку, повтор
того же endpoint снова вызывает существующую финализацию без записи ответов и смены времени
завершения. Для уже completed сессии lease не восстанавливается: scoped token разрешает
повторить продолжение/финализацию, но не редактировать ответы. Статус `processing` отображается
как обработка с ручным повтором, а не как готовый результат.

Клиент блокирует редактирование и новые autosave/heartbeat/events, пока ожидает завершение
или его повтор. Уже начатые autosave дожидаются завершения; их retry timers очищаются.
Поздний heartbeat/event не может увести со страницы до ответа completion. На ошибке остаются
сохраненный ввод и кнопка «Повторить завершение»; повтор не вызывает повторный batch/finalize.
Автоповторов completion нет. Если сервер вернул incomplete, форма снова доступна и указан
номер секции для проверки. `allowBack` не обходится. При включении в середине старого теста
ранее сохраненные неполные ответы могут потребовать исправления; приемку делать на новых тестах.

После успешного ответа используется `router.replace` на проверенный маршрут внутри той же
token-ссылки. При переходе к **другому тесту** загружается его серверная страница/overview,
создается новый controller/claim и используется новый deadline; это намеренно, в отличие
от переходов между секциями одной сессии. Старый контроллер не переносит ответы/кеш дальше.
В самом completion endpoint полные overview и вопросы больше не читаются.

При reload после сбоя последнего скоринга test page с completed-сессией, активным приглашением
и без запущенного следующего теста показывает экран «Ответы теста сохранены». Кнопка
«Продолжить оценку» повторяет completion POST без claim/ответов; GET не выполняет скоринг.
Если другая финализация удерживает claim, нужно дождаться результата либо восстановления
по прежнему TTL (5 минут). Приглашение уже completed идет на прежнюю страницу результата.

Истечение времени использует прежний expire/event/completion pipeline. При `expired` нового
RPC клиент делегирует ему выполнение. Этот путь, legacy Server Actions и внутренний скоринг
не оптимизированы в этой подзадаче; автоматического V1 fallback после ошибки нового RPC нет.

## Включение на staging

1. На актуальную схему применить только
   `supabase/migrations/20260907190000_assessment_completion_v2.sql`.
   Требуются существующие integrity schema, lease/answer V2 `20260906120000`/`20260906130000`,
   candidate/employee company/person/context/package/order columns. Для страницы — section
   read V2; для целой секции — batch migration `20260907150000` и ее зависимости.
   **Не запускать `tests/fixtures/*.sql` в Supabase**: они только для одноразового PGlite.
2. Выполнить read-only `supabase/verification/assessment_completion_v2.sql`:
   `installed=true`, `permissions_ok=true`. Она не завершает реальные тесты.
3. В серверном runtime установить `ASSESSMENT_COMPLETION_V2=true` при
   `SESSION_CONTROL_V2=true`, `ASSESSMENT_SECTION_READ_V2=true`,
   `ASSESSMENT_SOFT_NAVIGATION_V2=true`. Для `section` дополнительно
   `ASSESSMENT_SECTION_SAVE_V2=true`. Флаги без `NEXT_PUBLIC_`.
4. Перезапустить/переопубликовать приложение и провести приемку на новых тестовых назначениях.
   `ASSESSMENT_OVERVIEW_V2` и `ASSESSMENT_SECTION_PREFETCH_V3` независимы.

Агент не применял миграцию к удаленной БД, не включал реальные env и не завершал рабочие тесты.

## Откат

Выключить только `ASSESSMENT_COMPLETION_V2`, перезапустить runtime. Новые страницы используют
прежнее завершение: one-question session-control и terminal Server Action целой секции.
Не удалять RPC и не откатывать ответы/статусы.

Открытая V2-вкладка после выключения получит 409 и сохранит ввод. Дождаться подтвержденного
сохранения; не делать reload с несохраненными ответами. Если текущая сессия еще in_progress,
после reload используется старый путь. Если сессия уже completed, а скоринг прерван, старый
путь не предоставляет новый recovery screen: сначала восстановить финализацию с включенным
флагом или оставить V2 на staging до устранения сбоя. Не сбрасывать completed обратно в
in_progress и не отправлять старые ответы повторно ради обхода этой ситуации.

## Приемка и границы доказательств

Локально: `npm test`, `npm run typecheck`, `npm run lint`, `npm run build`.
`npm run test:browser:navigation` запускает localhost:4318, ожидается
`PASS: 30 browser scenarios`, затем Ctrl+C. Первые 16 — прежние секции/prefetch с выключенным
completion; 12 — новое завершение оба scope × one_question/section/empty × следующий/последний;
еще 2 — recovery. Используются реальные React-компоненты, синтетические HTTP/Server Action
и **имитация router.replace**, а не полный App Router. Вызов правильного маршрута проверен;
реальная RSC-навигация/переход через Next требуют staging E2E.

SQL-тесты исполняют новую миграцию с настоящими integrity/lease/answer migrations в PGlite
на минимальных fixtures. Проверены обязательность/optional/remediation/structured types,
owner/tenant/token/consent/device, повтор после commit, порядок следующего теста, отсутствие
повторной записи ответов, rollback на slow/failing trigger, истечение token/deadline и grants.
Это не конкурентный тест нескольких независимых соединений и не полная Supabase/RLS схема.

До production проверить в реальном Next.js + Supabase:

- Оба scope, оба режима, пустые/последние тесты и пакет из 2–3 тестов; все типы вопросов.
- На переходе: один completion RPC после ACK сохранения, без повторных answer upsert/full
  content reads; новая test page загружается через RSC без Document navigation.
- Новый тест: один новый claim, правильный порядок, новый timer/deadline без старых ответов.
- Double click, offline/timeout после commit, retry, reload recovery, ошибка скоринга,
  одновременное завершение/heartbeat/autosave/takeover/отмена из разных соединений.
- Все mandatory/optional/remediation и отсутствие скрытого обхода `allowBack`.
- Реальный scoring/report до/после (same answers → same results), processing/claim TTL,
  истечение времени через прежний pipeline, canary и откат с учетом recovery-ограничения.

Server operation `assessment.finish_session` измеряет новый RPC; `Server-Timing:
assessment_complete` — endpoint вместе со скорингом. Client `assessment.complete` в новом
пути измеряет ожидание completion (и дренирование старых записей), но не последующую RSC
загрузку/paint. `success` метрики означает успешный ответ, не обязательно готовность скоринга.

Снять 30+ cold/warm замеров отдельно для промежуточного и последнего теста: click-to-visible,
p50/p95, ошибки, объем, количество HTTP/RPC и нагрузку БД. Один RPC содержит несколько SQL
запросов, включая нормализацию по вопросам; его стоимость зависит от размера теста.
Локальные проверки подтверждают структуру пути, но не фактическое ускорение production.

Кодовая часть ручного завершения готова; performance/staging приемка всей программы открыта.
