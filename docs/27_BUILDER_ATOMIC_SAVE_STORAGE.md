# PERF-008.1 — Транзакционное хранилище конструктора

Дата: 08.09.2026. Статус: реализована и локально проверена **первая часть PERF-008**.
Сам PERF-008 не завершён. UI, server actions, debounce и публикация ещё используют V1.
Ускорение пользовательского autosave этим подшагом пока не достигнуто.

## Что реализовано

- Persistent `test_versions.builder_revision`. Ревизия монотонная, возвращается строкой
  во избежание потери точности bigint в JavaScript.
- Server-only `save_builder_delta_v2`: одна транзакция для изменённых секций, вопросов,
  вариантов, параметров версии и удалений. Успешный пакет повышает ревизию ровно на 1.
- Блокировка версии, повторная проверка активного шаблона, draft-статуса, компании,
  активного пользователя и его роли. Для системных тестов — platform_owner/platform_admin.
  Для компании — owner/admin/recruiter/super_admin. Company/user ID должен выводить сервер,
  не принимать из браузера. Создание тестов и company_test_permissions не изменяются.
- Проверка принадлежности UUID и родителей, запрет переноса между версиями, дубликатов,
  противоречащих upsert/delete и отсутствующих удаляемых сущностей.
- Перемещение выживших дочерних элементов до удаления родителей, чтобы CASCADE не потерял их.
- Сохранение неизвестных settings, scoring columns, media_url и существующих match_target_id.
  Сброс только подконтрольных редактору settings; новые matching target IDs создаёт БД.
- Последнее подтверждение хранит request ID, actor ID, исходную/результирующую ревизию,
  хеш payload и savedAt — без содержимого теста. Повтор того же запроса с тем же payload
  возвращает прежнее подтверждение без повторной записи. Старое подтверждение после
  следующей записи не позволяет перезаписать новую ревизию.
- Ошибка любого INSERT/UPDATE/DELETE откатывает также ревизию и регистрацию V2.

## Защита от смешивания V1 и V2

Первое успешное обращение к RPC регистрирует версию в приватной `builder_save_state`.
После этого обычные V1 записи и **V1 публикация** этого черновика отклоняются.
Разрешение записи живёт только внутри текущей транзакции RPC; клиент не может создать
его через JWT/параметр/настройку соединения. Таблица закрыта RLS и grants от anon/authenticated.

Для ещё не зарегистрированных версий старый редактор продолжает работать. Его изменения
версии и строк содержимого увеличивают ревизию; опубликованные/архивные данные остаются
неизменяемыми. Старые content writers теперь также берут lock версии. При конфликтном
порядке блокировок PostgreSQL может откатить одну транзакцию с deadlock; будущий клиент
обязан обрабатывать это ограниченным retry, не переходом к V1.

Установка миграции сама **не регистрирует** существующие версии. Однако новые row triggers
добавляют работу старому полнодокументному save. Поэтому до завершения PERF-008.2 эта
миграция предназначена для проверки на staging, **не для production rollout**.
Не вызывайте RPC на рабочих черновиках вручную: старый UI больше не сможет их сохранять
или публиковать. Просто выключить будущий flag после регистрации будет недостаточно:
безопасный rollback потребует совместимого revision-aware writer или отдельной процедуры
отключения при закрытых редакторах. Удалять `builder_save_state` для обхода защиты нельзя.

## Внутренний контракт RPC

Аргументы: `target_template_id`, `target_version_id`, `acting_user_id`, `target_company_id`
(NULL только для system scope), `expected_revision`, `request_id`, `delta`.
Ответ: `{ revision: string, savedAt: string, replayed: boolean }`.
`40001` означает конфликт/необходимость revision-aware writer; `42501` — недоступный scope,
права или чужой элемент; `55000` — не draft; `22023` — некорректный пакет.
Пользовательские сообщения должен формировать server action, не выводить сырой SQL error.

Все семь полей delta обязательны:

| Поле | Содержимое |
| --- | --- |
| version | NULL или полная группа редактируемых полей версии |
| sections | Только изменённые/новые заголовки секций, без questions |
| questions | Только изменённые/новые вопросы, без options |
| options | Только изменённые/новые варианты |
| deletedSections / deletedQuestions / deletedOptions | Массивы UUID удаляемых элементов |

Редактируемые поля передаются в snake_case, точный whitelist — в миграции.
Отсутствие элемента в массиве **не удаляет** его. Поля каждой переданной сущности обязательны,
nullable значения передаются явно. `settings_json` содержит только управляемые ключи:
version — presentation; section — contentBlocks; question — ключи текущего V1-конструктора.
RPC не принимает status, company_id, scoring_model/config, match_target_id и произвольные
settings. Лимит JSON — 8 MiB; пределы массивов сохраняют верхние границы текущей модели
(100 секций × 300 вопросов × 100 вариантов), а не увеличивают лимиты HTTP Server Actions.

**Это внутренний storage DTO, не готовый browser endpoint.** RPC проверяет структуру,
права, принадлежность, ревизию и ограничения БД. До вызова будущий server action обязан
собрать актуальный документ, применить прежнюю Zod/domain-валидацию, проверить remediation,
лимиты секций/вопросов/вариантов и очистить rich text. Чтение и валидация связываются с
expected_revision; при несовпадении нельзя автоматически применять старый delta к новой базе.

## Локальные проверки и staging

`tests/builder-save-v2-db.test.ts` исполняет реальную миграцию в PGlite, использует реальный
DDL таблиц и актуальные функции защиты публикации/архивации из миграций. 12 сценариев
(13 Node tests вместе с родительским): sparse option update, конфликт ревизий, lost ACK,
rollback после записи/удаления, move-before-delete, сохранение metadata, чужие IDs/parents,
некорректные пакеты, роли/status, V1 fence, published/archive/revert, grants и service-role.

Это не полностью мигрированный Supabase и не двухсоединительный PostgreSQL concurrency
test: два редактора проверяются последовательными запросами с общей исходной ревизией.
Полная RLS-матрица, реальные save/publish races, блокировки, latency и browser E2E остаются
staging-приёмкой. Все 439 Node tests, typecheck, lint и production build прошли.
Browser tests повторно не запускались — UI не менялся.

Для проверки в staging с ранее применёнными миграциями:

1. Применить **только** `supabase/migrations/20260908120000_builder_save_v2.sql`.
2. Выполнить read-only `supabase/verification/builder_save_v2.sql`: все passed должны быть
   true, enrolled_versions и unfinished_writes — 0 до первых тестовых V2-записей.
3. Проверить V1 на отдельном незарегистрированном черновике. Не активировать V2 пока нет
   следующего подшага. Никакие env-флаги сейчас менять не нужно.

**`tests/fixtures/builder-save-v2.sql` — только локальная заглушка для PGlite, не миграция.
Не запускать её в Supabase SQL Editor.** Внешняя БД этим изменением не затрагивалась.

## Следующий подшаг — PERF-008.2

1. Согласованный initial snapshot документа и revision для company/system builder.
2. Строгий browser delta DTO, dirty/deleted ID tracking и серверная сборка/валидация
   итогового документа; безопасные сообщения conflict/retry без раскрытия чужих данных.
3. Один in-flight save, debounce 1,5–2,5 с, coalescing, сохранение dirty до ACK,
   bounded backoff с тем же request ID и неизменным payload при неизвестном результате.
4. Flush перед preview/publish; revision-aware публикация с существующей полной
   publication/scoring-валидацией. CAS должен исключать изменение между проверкой и publish.
5. `BUILDER_SAVE_V2` default false, без автоматического V1 fallback; согласованный rollback
   с учётом зарегистрированных версий. Продумать также delete/revert/прочие редакторы draft.
6. Browser/contract/integration тесты; staging concurrency/RLS и измерение payload/latency.

До этих действий нельзя считать критерии PERF-008 выполненными.
