# PERF-004c/005c: предзагрузка следующей секции

## Изменение — 07.09.2026

Для candidate/employee и режимов `one_question`/`section` добавлена предзагрузка
неизменяемого содержимого следующей секции. Флаг `ASSESSMENT_SECTION_PREFETCH_V3`
по умолчанию выключен; первые страницы и completion/scoring этим шагом не изменены.

После открытия текущей секции и успешного claim контроллер ждет 500 мс и отправляет
`POST /api/assessment/section-prefetch`. Ответы, прогресс и текст обратной связи не
предзагружаются. Один read-only RPC выбирает следующую секцию закрепленной published/
archived версии. Без активной сессии, согласия, действующего token/deadline или при
несоответствии company/owner/session он ничего не возвращает. В one-question запрос
привязан к текущей канонической секции: нельзя цепочкой получить следующие незавершенные
секции. Review не предзагружается; режим section сохраняет прежнюю семантику чтения индекса.

Важно: текст следующей секции становится доступен в Network/памяти браузера раньше
ее показа. Это свойство предзагрузки, а не средство ограничения доступа к будущим
вопросам. Для тестов, где недопустима даже такая одна секция вперед, флаг не включать.
Правильные ответы/scoring keys и связи matching option→target в браузер не передаются.

Кеш существует только в памяти одного смонтированного контроллера: одна секция,
TTL 5 минут, максимум 1 MiB сериализованного UTF-8 DTO. Больший ответ не сохраняется;
лимит кеша не ограничивает размер обычного чтения и не гарантирует экономию трафика
уже скачанной предзагрузки. Ключ включает scope/token/session/исходную секцию, отдельно
проверяется целевой индекс. Нет общего кеша, localStorage, sessionStorage и CDN кеширования.
При смене секции, unmount, потере lock или offline кеш очищается, запрос отменяется.
Offline/saveData/2g пропускают запуск. Автоматических повторов предзагрузки нет.

## Переход и согласованность

1. Существующее сохранение/finalize или batch подтверждает текущие ответы.
2. Если готовой подходящей предзагрузки нет, выполняется обычный полный section-read V2.
   Ожидание незавершенной предзагрузки не добавляется к переходу: она отменяется.
3. При попадании в кеш `/api/assessment/section` получает только подсказку
   `{sectionId, versionId}` и вызывает `read_assessment_section_navigation_v3`.
4. RPC заново проверяет доступ и каноническую секцию. При совпадении возвращает
   свежие ответы, manifest/счетчики и разрешенную обратную связь — без текста вопросов,
   вариантов и content blocks. При расхождении (например, remediation) внутри того же
   RPC возвращает полный актуальный V2 snapshot, без дополнительного браузерного запроса.
5. Только успешный ответ разрешает объединить содержимое с новым состоянием и показать
   секцию. Удаленные/измененные ответы не восстанавливаются из кеша. Сохраненная ordering
   перестановка применяется после свежего чтения; deterministic shuffle/matching неизменны.

SQL — `STABLE SECURITY DEFINER`, `search_path=''`, execute только `service_role`.
Чтение не пишет ответы/lease/progress и не выполняет scoring. Raw SQL payload проходит
server-only allowlist/sanitizer; сырые связи вариантов или исторические scoring-поля
из `answer_json` клиент не получает. Все HTTP-ответы `private, no-store`, ошибки без token/SQL.
Ошибка обязательного чтения сохраняет текущую форму; speculative failure остается незаметной.

## Включение на staging

1. Сохранить существующие read/soft-navigation настройки. Поверх актуальной схемы применить
   только `supabase/migrations/20260907170000_assessment_section_prefetch_v3.sql`.
   Требуются предыдущий `20260906140000_assessment_section_read_v2.sql` и integrity schema
   с `deadline_at` для обоих scope. Для режима целой секции сохраняются требования шага 22.
   **Не запускать `tests/fixtures/*.sql` в Supabase**: это схемы одноразовых локальных тестов.
2. Выполнить `supabase/verification/assessment_section_prefetch_v3.sql` — read-only проверку.
   `installed`, `permissions_ok`, `stable_snapshot` должны быть `true`.
3. Установить серверный `ASSESSMENT_SECTION_PREFETCH_V3=true` при
   `ASSESSMENT_SECTION_READ_V2=true` и `ASSESSMENT_SOFT_NAVIGATION_V2=true`.
   Для `section` также нужны `ASSESSMENT_SECTION_SAVE_V2=true` и `SESSION_CONTROL_V2=true`.
   `ASSESSMENT_OVERVIEW_V2` независим. Перезапустить/переопубликовать приложение.
4. Открыть новый тест и выполнить приемку ниже. Реальные env и удаленную БД агент не менял.
   Выполнение предыдущей инструкции подтверждено пользователем, не удаленной проверкой агента.

Откат: `ASSESSMENT_SECTION_PREFETCH_V3=false` и перезапуск runtime. Старые открытые вкладки
могут послать уже запланированный speculative запрос (409, тихо игнорируется), но обязательный
переход с cached-подсказкой получит обычный полный V2 snapshot. Новые вкладки не предзагружают.
Удалять RPC/данные, выключать batch или soft navigation не нужно.

## Приемка и ограничения

Локальные команды: `npm test`, `npm run typecheck`, `npm run lint`, `npm run build`.
`npm run test:browser:navigation` запускает localhost:4318 с синтетическими данными;
ожидается `PASS: 16 browser scenarios`, затем остановить Ctrl+C. Реальные React-компоненты
проверяются с имитированными HTTP/Server Action, а SQL-миграции — в PGlite с минимальными
fixtures и реальными integrity migrations. Это не полный Next.js/Supabase/RLS E2E.

На staging для обоих scope и режимов проверить:

- После открытия — не более одного speculative запроса; review/последняя секция его не делают.
- При попадании в кеш после ACK по-прежнему есть свежее чтение, но ответ `kind=state` не
  содержит `section`, текста вопросов, вариантов или content blocks. Document/RSC/overview
  не запрашиваются на обычном переходе. Cache miss получает прежний полный snapshot.
- Все типы ответов, ordering/matching shuffle, optional skip, remediation и очистка ответа;
  Back/forward, reload/resume, пустая секция и завершение со старым scoring.
- Медленная/ошибочная предзагрузка, offline/reconnect, ответ старого запроса после unmount,
  другая вкладка/takeover, отмена token/согласия и deadline перед переходом. Кеш не должен
  позволять показать новую секцию без успешного актуального server read.
- Выключение флага без потери текущего ввода; существующие таймер, heartbeat и identity стабильны.

Предзагрузка добавляет один фоновый HTTP/RPC; обязательное чтение при переходе не исчезает.
Manifest/канонический выбор по версии все еще вычисляются в SQL. Выигрыш ожидается в
объеме и времени подготовки/передачи текста на критическом пути, не в общем числе запросов.
На маленьких секциях дополнительная нагрузка может перевесить выигрыш. До production
сравнить флаг off/on: 30+ cold/warm переходов, p50/p95 click-to-visible, размеры ответов,
ошибки и суммарную нагрузку БД; отдельно cache hit/miss. Не экспортировать реальные token/ответы.
Метрики `assessment.prefetch_section`, `assessment.load_section_state` — server operations;
`assessment.section_navigation` не включает предшествующую запись и painted frame.

Реальное ускорение еще не измерено. Кодовая подзадача prefetch готова; performance/staging
приемка и полный PERF-004/005 не закрыты. Следующая кодовая подзадача — завершение/смена теста.
