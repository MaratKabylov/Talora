# PERF-005b: мягкая навигация режима целой секции

## Что изменено — 07.09.2026

Режим `section` использует общий `AssessmentTestFlow` и тот же session controller,
что и `one_question`. Обычный переход больше не вызывает серверный redirect страницы:
после подтверждения секции загружается свежий snapshot, меняются форма, прогресс и URL.
Первый overview остается в памяти, timer/client/device/heartbeat не пересоздаются.
Полный серверный повторный вход намеренно создает новый экземпляр контроллера, чтобы
восстановить актуальные ответы и сбросить pending после серверной ошибки/redirect.

Новый `POST /api/assessment/section-save` вызывает один `save_assessment_section_v2` RPC.
Обычный переход: **один RPC записи + один RPC чтения секции**, без overview. Сюда не входят
уже начатые фоновые autosave, heartbeat, первая загрузка и завершение теста. SQL statements
внутри транзакции считаются отдельно; количество HTTP не является замером p95.

## Контракт сохранения

- Фоновые autosave режима целой секции сохранены. Перед batch блокируются новые очереди,
  отменяются отложенные таймеры и ожидаются уже начатые цепочки записей/повторов.
  Это предотвращает перезапись подтвержденного batch старым autosave из этой вкладки.
- В batch передаются ID секции, направление и ответы видимых вопросов. Сервер сам
  определяет состав секции и порядок по закрепленному `test_version_id`. Чужие/дублирующиеся
  ID, пропущенные основные вопросы и неверные обязательные ответы отклоняются.
- Вся запись, удаление очищенных ответов и lease находятся в одной транзакции.
  Ошибка нормализации/триггера или истечение deadline/token во время записи откатывает все.
  Нормализация использует проверенный helper PERF-003b; некорректные варианты отклоняются,
  а не подменяются пустым ответом. Scoring не меняется.
- Remediation определяется по текущему ответу родителя. При новом обязательном повторном
  вопросе основные ответы сохраняются, но переход вперед остается в текущей секции.
  Неактивный повторный ответ удаляется в той же транзакции. Время вопросов сохраняется
  только при включенном `captureQuestionTime`.
- При ошибке batch/чтения введенные данные остаются в форме. Повторный клик не отправляет
  еще один batch. При неопределенном сетевом исходе повтор использует идемпотентный upsert;
  автоматического fallback после ошибки V2 нет.
- Back/forward текущего test path учитывают `allowBack` и неподтвержденные изменения.
  История не переключает секцию во время незавершенных записей. Уход на другой маршрут,
  закрытие вкладки и reload не являются хранилищем неподтвержденного ввода.

Endpoint проверяет параметры, Origin и все необходимые флаги; ответы — `private, no-store`.
RPC доступен только `service_role`, с пустым `search_path`. Проверяются token, согласие,
company/owner/session chain, статус и lease. В ответе записи только deadline, время сохранения,
индексы и признак remediation; ключи правильных ответов, SQL/ошибки БД, PII не раскрываются.
Ответ чтения по-прежнему проходит безопасный presenter PERF-004a.

## Граница завершения

Последняя секция сначала подтверждается batch, включая remediation, затем отправляется
существующая HTML-форма Server Action для завершения/scoring. Эта операция повторно
сохраняет те же ответы и использует старые проверки/redirect; она не оптимизирована этим шагом.
При ошибках самого terminal Server Action действуют прежние правила восстановления страницы.
Пустой тест без секций также завершает прежний обработчик. Нормализация/lease batch атомарны,
но batch и последующее завершение **не являются общей транзакцией**.

## Включение

1. На staging поверх актуальной схемы применить
   `supabase/migrations/20260907150000_assessment_section_save_v2.sql`.
   Требуются lease/answer V2 миграции `20260906120000` и `20260906130000`, а для чтения —
   `20260906140000_assessment_section_read_v2.sql`. Тестовые `tests/fixtures/*.sql` в Supabase
   **не запускать**. Новая миграция добавляет RPC/права, не изменяет существующие ответы.
2. Выполнить `supabase/verification/assessment_section_save_v2.sql`: `installed` и
   `permissions_ok` должны быть `true`. Проверить также verification предыдущих lease/read RPC.
3. В серверном runtime установить `SESSION_CONTROL_V2=true`, `ASSESSMENT_SECTION_READ_V2=true`,
   `ASSESSMENT_SOFT_NAVIGATION_V2=true` и новый `ASSESSMENT_SECTION_SAVE_V2=true`.
   Перезапустить/переопубликовать приложение. Все флаги без `NEXT_PUBLIC_`.
   `ASSESSMENT_OVERVIEW_V2` независим и полезен для первой загрузки (со своей миграцией).
4. Провести приемку ниже. Агент не применял миграцию в удаленной БД и не менял реальные env.

Лимит запроса — 1000 видимых вопросов, 4000 символов текста ответа и 100 элементов
структурированного ответа. До включения убедиться, что опубликованные секции укладываются
в лимит; большие секции требуют отдельной стратегии, а не неявного обхода batch.

Откат: выключить только `ASSESSMENT_SECTION_SAVE_V2`, перезапустить runtime и открыть
тест заново. Режим целой секции вернется к старой форме, one-question soft navigation
останется доступна. Уже открытая V2-вкладка при попытке batch получит ошибку; не обновлять
ее с несохраненными данными, сначала дождаться подтвержденного autosave/сохранить ввод.
Удалять RPC или откатывать пользовательские данные не требуется.

## Проверки и приемка

Локально: `npm test`, `npm run typecheck`, `npm run lint`, `npm run build`.
`npm run test:browser:navigation` запускает изолированную fixture на localhost:4318;
в браузере дождаться `PASS: 30 browser scenarios` (расширено шагами 23–24), после проверки остановить Ctrl+C.
Синтетические transport/профили не используют рабочую БД и реальные ключи.

SQL-тесты исполняют реальную миграцию, нормализатор и существующие answer triggers
в PGlite: оба scope, structured types, атомарный rollback записи/удаления/lease,
истечение во время медленного trigger, consent/tenant/lease, remediation и права.
Route/page тесты проверяют все флаги, изоляцию параметров и единственный RPC записи.
Browser-component тесты проверяют оба режима × оба scope × `allowBack`, ошибки,
двойной клик, ожидание autosave, восстановление/историю, remediation, timer/identity/
heartbeat и передачу последней формы в имитированный legacy action.

Это не полный Next.js/Supabase E2E и не конкурентный тест через отдельные соединения.
На staging отдельно проверить все типы полей, пустые/последние секции, переподключение,
закрытие/повторное открытие, takeover другой вкладкой, отмену приглашения, deadline,
ошибку terminal action и реальный scoring. В Network проверить отсутствие Document/RSC
test-page/overview запросов на обычном переходе; не экспортировать реальные token/ответы.

Метрика `assessment.save_section` в server logs и Server-Timing измеряет RPC записи;
`assessment.section_navigation` — последующее чтение/применение snapshot. Отдельно снять
30+ cold/warm click-to-visible замеров с учетом ожидания autosave, записать p50/p95 и ошибки
в `docs/17_PERFORMANCE_BASELINE.md`. Реальное ускорение пока не измерено.

Prefetch и оптимизация завершения/смены теста остаются следующими работами; полный
PERF-004/005 и staging-приемка не закрыты.

Продолжение: кодовая подзадача prefetch реализована отдельно, включение и новая миграция
описаны в `docs/23_SECTION_PREFETCH_ROLLOUT.md`. Завершение/смена теста еще не оптимизированы.
