# PERF-004a: чтение активной секции

## Объем изменения

Оба маршрута прохождения теста (кандидат и сотрудник) используют общий server-only reader.
При `ASSESSMENT_SECTION_READ_V2=true` один HTTP RPC-вызов `read_assessment_section_v2` получает:

- метаданные секций и счетчики всех/видимых/неотвеченных вопросов;
- вопросы, варианты, инструкции и сохраненные ответы только выбранной секции;
- индекс секции с учетом one-question/review режима и прогресса.

RPC проверяет token, согласие, срок приглашения, принадлежность session и company, активный
статус. Чтение использует единый STABLE snapshot и не изменяет lease/ответы. Исполнение
разрешено только `service_role`; клиент вызывает сервер приложения, не RPC напрямую.

Серверный presenter сохраняет детерминированный shuffle и санитизацию rich text, отделяет
matching targets от вариантов, фильтрует answer JSON и исключает scoring keys, points,
competency effects и `is_correct` из DTO чтения. `remediationRequired` передает только
необходимость показать повторный вопрос. Прежний контракт ответа session-control API
(`answerIsCorrect` для интерактивного feedback) не изменен в этом шаге.

При выключенном флаге сервер продолжает читать полный legacy content, но в браузер также
передаются только ответы выбранной секции. При включенном флаге ошибка RPC не вызывает
скрытый fallback: возвращается обычная ошибка загрузки без token/SQL в сообщении.

## Что пока не изменено

- Без `ASSESSMENT_OVERVIEW_V2` полный company/job/package/session overview по-прежнему
  загружается на сервере. PERF-004b от 07.09.2026 добавляет отдельный компактный reader;
  включение описано в `docs/20_ASSESSMENT_TEST_OVERVIEW_ROLLOUT.md`.
- Сохранение секции и завершение/scoring используют существующие server actions/readers.
- Межсекционная навигация и предзагрузка не оптимизированы; это продолжение PERF-004/005.
- Смена секции сейчас перемонтирует форму, чтобы не сохранить локальные ответы предыдущей
  секции. Lease identity остается в sessionStorage; сохранение mounted session относится к PERF-005.
- Правила публикации остаются прежними: remediation target — ниже родителя в той же секции,
  без повторного использования target. Уже опубликованный контент не изменяется.

Полный PERF-004 не считается завершенным этим изменением.

## Применение и проверка

1. В staging применить **только** новую миграцию
   `supabase/migrations/20260906140000_assessment_section_read_v2.sql` поверх актуальной схемы
   проекта. Она добавляет read-only функцию и права, не переносит и не удаляет данные.
   **Не запускать `tests/fixtures/*.sql` в Supabase:** это минимальная схема только для локальных тестов.
2. Выполнить `supabase/verification/assessment_section_read_v2.sql`. Это безопасная read-only
   проверка: `installed`, `permissions_ok`, `stable_snapshot` должны быть `true`.
3. Установить `ASSESSMENT_SECTION_READ_V2=true` только в серверном staging runtime,
   затем перезапустить/переопубликовать приложение. Не добавлять префикс `NEXT_PUBLIC_`.
   Флаг независим от `SESSION_CONTROL_V2`; проверить новый reader с обоими режимами записи.
4. На синтетических приглашениях кандидата и сотрудника проверить: section/one-question,
   reload с восстановлением всех типов ответов, переходы и review с allowBack true/false,
   remediation после неверного ответа, пустые секции, завершение и истечение таймера.
   Чужая session, отозванное согласие и истекший/отмененный token не должны раскрывать контент.
5. В HTTP trace от сервера к Supabase убедиться: после overview выполняется один read RPC,
   а не загрузка всех вопросов/ответов. Проверить клиентский payload на отсутствие ответов
   других секций, scoring metadata и соответствий правильных matching-пар. Не сохранять
   реальные token/PII в trace или отчете.
6. Сравнить размер payload и 30+ cold/warm замеров `assessment.load_section`, TTFB test page
   и перехода между секциями при одинаковом количестве секций, но разном числе вопросов
   вне активной. Отдельно замерить рост числа секций: manifest растет с их количеством.
   Записать результаты в `docs/17_PERFORMANCE_BASELINE.md` перед production rollout.

## Локальное подтверждение и ограничения

`tests/assessment-section-v2.test.ts` исполняет настоящий SQL в PGlite, настоящие reader,
presenter и обе страницы с имитацией транспорта. Проверяются права, отсутствие записей,
tenant/token/consent/status guards, выбор секции, восстановление ответов, shuffle и фильтрация DTO.
В синтетическом тесте добавление 1000 длинных вопросов вне активной секции меняет размер
ответа RPC менее чем на 20 символов (только счетчики). Это проверка объема, не замер p95.

PGlite использует минимальную тестовую схему, не полный Supabase/RLS runtime. Браузерный
smoke test, планы SQL и фактическая производительность на staging остаются обязательными.
Агент не применял новую миграцию к удаленной БД и не включал флаг в реальном окружении.

## Откат

Установить `ASSESSMENT_SECTION_READ_V2=false` и перезапустить серверный runtime.
Данные и режим записи не меняются; read RPC можно оставить в БД с server-only правами.
Удалять функцию или откатывать схему для возврата на старое чтение не требуется.
