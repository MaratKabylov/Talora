# AGENTS.md — Talvia / HR Assessment SaaS

Платформа: вакансии, системные и собственные тесты, приглашения по ссылке, отчёты и сравнение кандидатов.
Стек: Next.js App Router, TypeScript, Supabase/PostgreSQL/Auth/RLS, Tailwind, shadcn/ui, React Hook Form, Zod, TanStack Table.

## Начало задачи и контекст

- В новом чате или после потери контекста прочитай `docs/CURRENT_STATE.md`. В текущем чате не перечитывай неизменённые документы, уже доступные в контексте.
- Перед изменениями проверь `git status --short` и структуру затронутого модуля. Сохраняй чужие изменения.
- Выполняй одну согласованную задачу. Текущий PERF-план: `docs/16_PERFORMANCE_OPTIMIZATION_PLAN.md`; исходные MVP milestones: `docs/04_BACKLOG.md`. Не начинай bootstrap заново по старым незаполненным чекбоксам.
- Читай раздел задачи и необходимые зависимости, а не весь проект. Начинай с `rg`/`rg --files`, затем открывай нужные участки. При неясности расширяй проверку.
- Для вопроса о статусе достаточно актуального состояния и подтверждающих источников; не меняй файлы и не запускай сборку без необходимости.

## Документы по типу задачи

- Продуктовые требования и границы MVP: `docs/00_MASTER_PROMPT_FOR_CODEX.md`, `docs/01_PRODUCT_SPEC_MVP.md` — относящиеся к задаче разделы.
- БД: нужные таблицы в `docs/02_DATABASE_MODEL.sql` и относящиеся миграции в `supabase/migrations/`. Базовый SQL не заменяет историю миграций и проверку реальной БД.
- Auth, RLS, tenant-доступ, token flow, server-only RPC: обязательно `docs/06_RLS_AND_SECURITY_NOTES.md` и действующие проверки/политики затронутого пути.
- Seed и системные тесты: `docs/03_SEED_SYSTEM_TESTS.json` и соответствующий код загрузки.
- Оптимизация: нужный PERF-раздел, связанная rollout-инструкция; `docs/17_PERFORMANCE_BASELINE.md` — при замерах или проверке результатов.
- Не загружай все перечисленные документы автоматически. Этот порядок чтения и проверок заменяет прежние общие требования перечитывать весь комплект и собирать проект после любой правки документации.

## Обязательные ограничения

- Multi-tenant: бизнес-данные привязаны к `company_id` непосредственно или через проверенного родителя; изоляция через RLS. Server-only privileged код дополнительно проверяет роль, tenant и ownership; не доверяй клиентскому `company_id`.
- Кандидат проходит по invitation token без регистрации; проверяй срок/статус и принадлежность сессии. Не открывай общий anon-доступ к таблицам. Сохраняй согласие на обработку данных.
- Содержимое опубликованных версий неизменяемо; правки через новую версию. Результаты ссылаются на конкретный `test_version_id`. Узкую отмену неиспользованной системной публикации не расширяй: условия в security notes, проверки и аудит атомарны.
- Сравнение только в рамках вакансии; сохраняй `overall_score` и `fit_score`. Не используй чувствительные признаки для скоринга.
- Secret/service role key — только на сервере. Не выводи секреты, invitation tokens и персональные данные в логи. Новые env документируй в `.env.example`, не придумывай ключи.
- Не применяй удалённые миграции, не включай production-флаги и не делай destructive/downgrade-операции без соответствующего разрешения. `tests/fixtures/*.sql` — локальные заглушки, не миграции для Supabase.

## Реализация, проверки и передача

- Делай минимальное законченное изменение без попутного рефакторинга. Не запускай субагентов без явного запроса пользователя.
- Во время разработки запускай профильные тесты. После крупного изменения кода — `npm run lint`, `npm run typecheck`, `npm run build` и необходимую регрессию (`npm test`, профильные browser scripts из `package.json`). Повторяй проверки, если последующие правки затронули проверенный путь.
- Для изменений только Markdown проверяй diff, ссылки и согласованность; сборка/тесты приложения не нужны. Проверки RLS, миграций, целостности и скоринга ради экономии не пропускай.
- Для успешных команд показывай краткий итог, для ошибок — достаточные детали. Не загружай полные логи, generated-файлы и большие diff без необходимости. Не считай старый запуск тестов текущей проверкой.
- После реализации или перед передачей незавершённой работы обнови `docs/CURRENT_STATE.md`: дата, этап, изменённые области, проверки, ограничения и следующий шаг. Это краткий снимок (ориентир до 60 строк), не журнал; детали оставляй в плане/rollout-документе.
- Разделяй «код готов», «локально проверено», «миграции применены» и «staging/production принят». Неизвестное отмечай явно; состояние сверяй с кодом и свидетельствами, а не принимай за доказательство.
- Отвечай кратко: результат, проверки, оставшийся риск/следующий шаг. Не обещай процент экономии токенов без замеров.
